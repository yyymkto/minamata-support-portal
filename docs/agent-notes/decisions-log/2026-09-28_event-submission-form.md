# [2026-09-28] イベントタブに主催者からの投稿フォーム（承認制）を追加する

**決めた人/エージェント**: 吉野さん（Claude Codeの提案を受けて）
**関係者**: 吉野さん、Claude Code、Antigravity

## 背景・課題

吉野さんから「水俣市でイベントを企画している人がフォームから投稿し、認証されればページに反映される仕組みを追加したい」
という相談があった。イベントタブ新設時（`2026-09-21_events-tab.md`）には「主催者からの投稿フォーム」を
v1では入れず、反応を見て検討するとしていたもの。

## 決定内容

- Googleフォームで受け付け、回答は既存のイベント登録用スプレッドシートの新しいタブに保存する。
- 吉野さんが「承認」列に書いた行だけを、数式で「掲載用」タブに抜き出し、そのタブだけをCSVで公開する。
  `update_events.py` が既存の手動登録分と同じ仕組みで読み込み、翌朝の自動更新で載せる。
- 以下はClaude Codeの想定どおりで進める（吉野さん了承）：
  承認者は吉野さん1人／連絡先メールアドレスは必須・非公開／チラシ画像は受け付けない／
  フォームに非公式サイトである旨と掲載基準を載せる／「新規・変更・中止」の種別を最初から入れる／
  シートを読めなくなったときにIssueで知らせる。
- 優先順位は「自動抽出 < フォーム < 吉野さんのシート1」。シート1の非表示行でどの経路のイベントも消せる。
- シートの読み込み失敗は、イベントタブ設計時の「Issueを起票しない」を改め、Issueで知らせる（ワークフローは止めない）。

詳細は `design-specs/2026-09-28_event-submission-form.md`。

## 検討した他の案

- 回答シートをそのまま公開する：連絡先が誰でも見られ、`_events_*.json` 経由でリポジトリとPagesにも残るため不可。
- フォームサービスやサーバーを別に用意する（Netlify Forms等）：静的サイト・GitHub Pagesの構成から外れ、運用の手間が増えるため見送り。
- 変更・中止をスクリプトで自動反映する：どの掲載が対象かを機械的に特定しにくく、なりすましで他人のイベントを消される危険があるため、
  吉野さんが承認を付け替える運用にした。

## 長期運用で懸念される点（吉野さんに説明済み）

承認の属人化、掲載基準の必要性、投稿後の変更・中止、連絡先の蓄積、シート構造の破損に気づきにくいこと、
重複・迷惑投稿、Google側の仕様変更。対策は設計書の「運用」「既知の制限」に記載。

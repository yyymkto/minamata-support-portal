## 概要

市の広報紙「広報みなまた」の新しい号を自動で見つけ、PDFからイベントを取り出して「イベント」タブに載せる。
広報の「くらしの伝言板」には市サイトの記事にならない催し（こどもセンター、もやい館の講座、地区の祭りなど）が多い。
2026年11月号から選んだ11件を調べたところ、11件ともお知らせにもイベント一覧にも載っていなかった。

対象はイベントのみ。広報からの制度情報の抽出は別の設計書で扱う（人の確認を挟むIssue通知を想定）。

## 実データで確認したこと（2026-11-02）

- 一覧ページ `https://www.city.minamata.lg.jp/list00422.html` に、各号が「広報みなまた令和8年11月号」のリンクで並ぶ。
- 各号の記事ページ（例 `/kiji0034938/index.html`）にPDFが1つある（10月号・11月号で確認）。
- PDFは約11〜13MB。1ページに紙面の見開き2ページが入っている（11月号は17ページ、10月号は19ページ）。
- `pypdf` で全ページから文字を取り出せる。1ページあたり多くて約3,600字。OCRは不要。
- 文字が取れないページがある。11月号の10ページ目は、ローズフェスタと九州和紅茶サミットのチラシ画像だった。
- 11月号の記事ページの更新日は2026-10-30で、発行月の前月に公開される。
- 年を省いた日付（`12/12`）、紙面の順序の崩れ、誤字（「紅茶」→「紅荼」）、自治会の担当者の氏名・携帯番号がある。

## データ構造

### `public/data/_events_koho.json`（新規・自動生成、UIからは不参照）

```
{
  "last_list_ok_date": "YYYY-MM-DD (必須。一覧と号の解析が最後に成功した日)",
  "issues": {
    "<記事ページURL>": {
      "title": "string (必須。例: 広報みなまた令和8年11月号)",
      "issue_month": "YYYY-MM (必須)",
      "pdf_url": "string (必須)",
      "pages_done": [2, 3, 4],
      "pages_skipped": [1, 10],
      "events": [ イベント ]
    }
  }
}
```

イベントの形は `events.json` の既存項目と同じ。次の3項目だけ広報用の値にする。

| 項目 | 値 |
|---|---|
| `origin` | `"koho"` |
| `source_url` | `<pdf_url>#page=<PDFのページ番号>&event=<タイトルと開始日のハッシュ10桁>` |
| `source_label` | `広報みなまた11月号（PDF 13ページ）` |

`source_url` をイベントごとに別の値にするのは、既存の上書き・非表示の処理がURLで対象を決めるため。
PDFのURLをそのまま使うと、1件の非表示で同じ号の全イベントが消える。

## 処理仕様

`update_events.py` に広報の処理を足す。実行は毎朝の `daily-update.yml` の中で行う。

1. **号の検知（毎日）**: 一覧ページを1回取得し、`広報みなまた令和N年M月号` の形のリンクを読む。全角数字も受け付ける。合併号は最初の月を `issue_month` とする。
2. **対象の選択**: 未処理の号と、`pages_done` と `pages_skipped` で全ページが埋まっていない号を処理する。初回は最新号だけを処理し、過去の号はさかのぼらない。
3. **PDFの取得**: 記事ページからPDFのリンクを取る。PDFはリポジトリに保存しない。
4. **ページごとの抽出**: `pypdf` で1ページずつ文字を取る。200字未満のページはGeminiに送らず `pages_skipped` に入れ、ログに残す。それ以外は1ページ1回Geminiを呼ぶ。
5. **確認**: 次の「抽出後の確認」に通ったものだけ `events` に入れる。
6. **保存**: ページごとに完了を記録する。Geminiが失敗したページは翌日に再実行する。連続失敗の打ち切りは既存の `GEMINI_CONSECUTIVE_FAILURE_LIMIT` を使う。
7. **統合**: 下の「統合の順序」で `events.json` に入れる。終了済みイベントは既存処理で外れる。終了済みイベントしか残っていない号は、`events` を空にして号の記録だけ残す（再処理を防ぐため）。

### Geminiへの指示

入力は今日の日付、号の名前、発行年月、PDFのページ番号、ページ本文。出力は `{"events": [...]}` で、各要素は既存の抽出項目（`start_date` から `registration_note` まで）に `title` を足したもの。

- **対象**: 水俣市内で開かれ、一般の人が参加・観覧・来場できる催し。祭り、展示、公演、講座、教室、体験会、交流会、地区の文化祭を含む。
- **対象外**:
  - 水俣市外の会場の催し（芦北町・津奈木町など）
  - 個別相談会、常設の相談窓口
  - 開催済みの報告（フォトリポート、まちのわだい）
  - 募集だけの告知、市の手続きのお知らせ
- **1件の単位**: 名前の違う催しは別々の1件にする（こどもセンターの①〜⑦は7件）。同じ名前の連続講座は1件にし、`start_date` は初回、`end_date` は最終回、各回の日付は `summary` に書く。
- **年**: 省略された年は発行年月から補う（11月号の `3/13` は翌年）。
- **個人情報**: 個人の氏名と携帯電話番号は出力しない。`organizer` は団体名だけにし、団体名が分からなければ null にする。

### 抽出後の確認（プログラム側）

Geminiの結果をそのまま信じず、次の確認で落とす。落とした件はログに残す。

| 確認 | 落とす条件 |
|---|---|
| 日付の範囲 | `start_date` が発行月の前月1日より前、または発行月の12か月後より後 |
| 日付の裏づけ | NFKC正規化と空白除去の後のページ本文に、前後に数字が続かない `M/D` も `M月D日` も無い（カレンダーのページは下記） |
| 申し込み | 既存の `registration_from_article()` にページ本文を渡す |
| 携帯番号 | 各文字列項目の `0[789]0-?\d{4}-?\d{4}` を消す。`registration_note` が空になれば null |
| 市外 | `venue` に「芦北」「津奈木」を含む |

### 設計変更: カレンダーの扱い（2026-11-02、タスク3の結果による）

「くらしのカレンダー」を含むページでは、日付が「21 土」の形式で書かれている。

- **日付の裏づけ:** 通常の確認に加えて、開始日が発行月の日付で、「日の数字＋その日の正しい曜日」の並びが本文にあれば通す（例: 2026-11-21 は `21土`）。
- **開始日:** 月初の行に「【～11/15】」が付く催しは前月から続いている場合があるため、そのページだけでは開始日を決められない。この形は出力しない。
- **説明文と申し込み:** カレンダーには名前・時刻・会場しか無いため、`summary` と `registration` は null にする。名前から内容を想像して書かない。

### 統合の順序

`build_events()` を次の順にする。

1. 自動抽出分を `dedupe_events()` でまとめる（既存）
2. 投稿フォーム分を足す（既存）
3. 広報分を足す（新規）
4. 手動登録の上書き・非表示を適用する（既存）
5. `drop_koho_duplicates()` を実行する（新規）

`drop_koho_duplicates()` は、開始日が同じで、`normalize_title()` 後のタイトルの一方がもう一方に含まれるイベントを同じものとみなす。

- 広報以外の経路と重なれば、広報分を捨てる（記事ページのほうが軽く、詳しく開けるため）。
- 広報どうしで重なれば、新しい号を残す。

### 異常の通知

次のどれかで、ステップ出力 `koho_error=true` と `koho_error_detail` を書き出す。ワークフローは止めない。

- 一覧または号の解析の失敗が3日続いた（`last_list_ok_date` で判定）
- 最新号の `issue_month` が今月より2か月以上古い
- 全ページ処理した号のイベントが0件

## 設計判断の理由（なぜこの設計にしたか）

- **毎月の決まった日ではなく毎日確認する**: 公開日は月によって変わる（11月号は10/30）。毎朝の処理なら公開の翌朝に拾える。新しい号が無い日の負担は一覧ページ1回の取得だけで、Geminiは呼ばない。
- **別のスクリプトにせず `update_events.py` に足す**: 上書き・重複除去・`events.json` の書き出しと順序が絡むため、同じ処理の中に置く。
- **ページごとに抽出する**: ページ番号を正確に持て、申し込みの裏づけを1ページの本文で確認でき、失敗したページだけ翌日に再実行できる。1ページ約3,600字以内で、1号17〜19回の呼び出しで済む。
- **pdftotextではなくpypdf**: GitHub Actionsに追加パッケージを入れずに済む。
- **人の確認を挟まず掲載する**: 終了すれば自然に消え、誤りがあっても手動の非表示で止められる。公開前のタスク3で精度を確かめる。
- **画像チラシは初版では読まない**: 確認した1ページの2件はどちらも市サイトから掲載済みだった。AIに画像を読ませる処理は、見逃しが実際に出てから検討する。
- **相談会を対象外にする**: イベントタブは参加する催しの一覧で、定期の相談窓口とは性質が違う。不要な呼び出しも減らせる。
- **市外の催しは載せない**: 2026-11-02の吉野さんの判断。

# [2026-09-28] イベント投稿フォーム（主催者からの掲載申し込み） 設計書

**設計者**: Claude Code
**実装担当**: 吉野さん（タスク1〜2：フォーム・シート準備）、Claude Code（タスク3〜5：収集スクリプト・ワークフロー・手順書、タスク7：公開範囲の確認）、Antigravity（タスク6：UI）
**状態**: 全タスク完了（タスク1〜7完了。吉野さんから回答用フォームURL受領・EVENT_FORM_URL設定完了）

## 概要

水俣市内でイベントを企画している人が、Googleフォームからイベントの掲載を申し込めるようにする。
吉野さんが内容を確認して「承認」した申し込みだけが、翌朝の自動更新でイベントタブに載る。

既存のイベントタブ（設計書 `2026-09-21_events-tab.md`）のスプレッドシート連携を土台にし、
「フォーム → 回答シート（非公開）→ 承認済みの行だけを抜き出す掲載用シート（CSV公開）→ `update_events.py`」という流れにする。
サーバーや有料サービスは使わない。

### 前提（2026-09-28、吉野さんと合意）

- 承認するのは吉野さん1人（2人目を置く場合の手順は手順書に書く）。
- 投稿者の連絡先（メールアドレス）は必須。確認のためだけに使い、公開しない。
- チラシ画像は受け付けない（Googleフォームで画像を受け付けると投稿者のGoogleログインが必須になり、表示側の作り込みも増えるため）。
  代わりに「リンク」欄にInstagram投稿などのURLを書いてもらう。
- フォームには「新規／変更／中止」の種別を最初から入れる。
- シートを読めなくなったときにIssueで知らせる仕組みを最初から入れる。

## 全体の流れ

```
企画者 ──Googleフォーム──▶ 「フォームの回答」タブ（非公開・連絡先を含む）
                               │ 吉野さんが内容を確認し、「承認」列に x を書く
                               ▼
                          「掲載用」タブ（数式で、承認済み・中止以外の行の、掲載する列だけを抜き出す）
                               │ このタブだけをCSVとしてウェブに公開
                               ▼
             update_events.py（EVENTS_FORM_CSV_URL）→ events.json → 翌朝7:00にサイトへ反映
```

- フォームの回答は、既存の「くらしナビ イベント登録」スプレッドシートに新しいタブとして保存する
  （吉野さんが見るシートを1つにまとめるため）。既存の登録用タブ（シート1）には手を加えない。
- **「フォームの回答」タブは絶対にウェブに公開しない。** 公開するのは「掲載用」タブと既存のシート1だけ。

## データ構造

### Googleフォームの質問

質問のタイトルは、掲載用タブの数式が見出しの文字で列を探すため、**下の表の「質問のタイトル」の文字どおり**にする。
補足の説明は、質問の「説明」欄に書く。

| セクション | 質問のタイトル | 形式 | 必須 | 入力チェック・説明 |
|---|---|---|---|---|
| 1 | 種別 | ラジオボタン | 必須 | 「新規の掲載」「掲載内容の変更」「中止・掲載取り下げ」。回答に応じてセクション2か3に進む |
| 1 | 同意 | チェックボックス | 必須 | 「掲載基準と注意事項を確認しました」1つだけ |
| 2（新規・変更） | 変更するイベント | 記述式 | 任意 | 説明：「『掲載内容の変更』のときだけ、今載っているイベント名と開催日を書いてください」 |
| 2 | イベント名 | 記述式 | 必須 | 最大40字 |
| 2 | 開始日 | 日付 | 必須 | 年を含める設定にする |
| 2 | 終了日 | 日付 | 任意 | 説明：「複数日のときだけ」 |
| 2 | 時間 | 記述式 | 任意 | 例：10:00〜15:00 |
| 2 | 場所 | 記述式 | 必須 | 例：道の駅みなまた |
| 2 | 概要 | 段落 | 必須 | 最大120字（回答の検証「文字数の最大値」） |
| 2 | 主催 | 記述式 | 必須 | 説明：「サイトに表示されます。団体名か、個人の場合は表示してよいお名前を」 |
| 2 | リンク | 記述式 | 任意 | 回答の検証「URL」。説明：「詳しい情報が載っているページ（Instagram投稿など）」 |
| 3（中止） | 中止するイベント | 段落 | 必須 | 説明：「イベント名と開催日、中止か取り下げかを書いてください」 |
| 最後 | 連絡先メールアドレス | 記述式 | 必須 | 回答の検証「メールアドレス」。説明：「内容の確認のためだけに使い、公開しません」 |

- 「メールアドレスを収集する」設定は使わない（「確認済み」はGoogleログイン必須になるため。連絡先は通常の質問で聞く）。
- 「回答を1回に制限する」はオフ（ログイン必須になるため）。
- 回答の送信後の編集はオフ（変更は「掲載内容の変更」で出し直してもらう。承認済みの内容が知らないうちに変わるのを防ぐ）。

### 「フォームの回答」タブ（非公開）

フォームが自動で作る列（タイムスタンプ＋上の質問）の右に、吉野さんが次の2列を手で足す。

| 列名 | 内容 |
|---|---|
| 承認 | 空欄なら載せない。何か書いてある行（例：「x」）は載せる。取り下げるときは消す |
| メモ | 任意。「重複のため見送り」「〇/〇 電話で確認済み」など吉野さん用 |

- 並び順は変えてもよい（数式は見出しの文字で列を探すため）。

### 「掲載用」タブ（CSV公開）

1行目の見出しは既存のシート1と同じ名前にする（`update_events.py` の `parse_sheet_csv` をそのまま使えるように）。

```
イベント名 / 開始日 / 終了日 / 時間 / 場所 / 概要 / 主催 / リンク
```

- 2行目以降はA2セルの数式1つで作る（手で書き込まない）。条件：
  - 「承認」が空欄でない、かつ「種別」が「中止・掲載取り下げ」でない行だけ。
  - 開始日・終了日は `TEXT(…, "yyyy/mm/dd")` で文字列にする（掲載用タブのセルの表示形式に左右されないように）。終了日が空欄の行は空欄のまま。
  - 列は「フォームの回答」タブの1行目から見出しの文字で探す（`XMATCH` 等）。**列の位置（A列・B列…）で指定しない**
    （フォームに質問を足すと、回答タブの列の並びが変わるため）。
  - 「連絡先メールアドレス」「メモ」「同意」「タイムスタンプ」は含めない。
- 数式の本体は、実際のシートで動作を確かめてから手順書（タスク5）に載せる。
- 「非表示」「情報元」列は置かない。情報元は既存の既定ルール（リンクがInstagramなら「Instagram」、それ以外は「詳細を見る」表示）に任せる。

### 「変更」「中止」の扱い（運用で行う。スクリプトでは自動処理しない）

- **変更**：新しい内容で申し込みが1行増える。吉野さんは新しい行に「承認」を書き、`変更するイベント` に書かれた元の行の「承認」を消す。
  変更の対象が自動で載ったイベント（市のサイト等）の場合は、既存どおりシート1に上書き行を足す。
- **中止**：中止の行は掲載用タブに出ない（通知の役割だけ）。吉野さんは元の行の「承認」を消す。
  対象が自動で載ったイベントの場合は、シート1に非表示行を足す。
- v1ではサイトに「中止」と表示せず、一覧から消すだけにする。

### `public/data/_events_form.json`（新規・内部用、UIからは参照しない）

最後に掲載用タブを読み込めたときの内容。`_events_manual.json` と同じ形。CSVを取得できなかった日はこれを使う。

```
{
  "fetched_at": "ISO8601",
  "events": [ events.json の item と同じ形（origin='form'） ],
  "hidden_urls": [],
  "warnings": [ "3行目: …" ]
}
```

- `_events_manual.json` と同じく、このファイルもリポジトリにコミットされ、GitHub Pagesにも配置される（誰でも見られる）。
  承認済みで掲載する内容しか入らないので問題ないが、**連絡先がここに入らないこと**をタスク3・7で確認する。

### `events.json` の変更

- `origin` に `'form'` を追加する（`'auto' | 'manual' | 'form'`）。UIは `origin` を参照していないので、画面には影響しない。
- `id`：`'f-' + sha1(イベント名+開始日+リンク)` の先頭10桁（手動の `'m-'` と区別する）。

## 処理仕様（`scripts/update_events.py` の変更）

1. **読み込み**
   - 環境変数 `EVENTS_FORM_CSV_URL` を追加し、既存の手動分と同じ関数で読む（`load_manual` を「URL・キャッシュのパス・`origin`・`id` の接頭辞」を引数に取る形に一般化する）。
   - 取得失敗・見出し不一致のときは `_events_form.json` の前回分を使う（既存の手動分と同じ）。
   - 未設定なら投稿分なしとして続行する。
2. **統合の優先順位**：自動抽出 < フォーム < シート1（吉野さんの手動登録）
   - まず、フォーム分のリンクが自動抽出分の `source_url` と一致すれば、フォーム分で置き換える（主催者の情報を優先する）。
   - 次に、既存の `merge_manual` で、シート1の上書き・非表示を「自動抽出分＋フォーム分」に適用し、シート1の手動分を足す。
     これにより、**吉野さんはシート1の非表示行で、フォーム分も含めてどれでも消せる**（承認を消し忘れた場合の保険）。
   - シート1とフォームで同じリンクの行がある場合は、シート1の行だけを残す。
   - リンクが空のフォーム分は、リンクでの上書き・非表示の対象にならない（承認を消して取り下げる）。
3. **失敗の通知**
   - 次のどちらかに当てはまったら、「読み込めなかったシート」の名前を記録する：
     (a) URLが設定されているのにCSVを取得できない、(b) 見出し行に必須列（イベント名・開始日）がない、
     (c) セルにスプレッドシートのエラー値（`#N/A` `#REF!` `#VALUE!` `#NAME?` `#ERROR!` `#DIV/0!` `#NUM!` `#NULL!` で始まる値）がある。
     対象はシート1（`EVENTS_SHEET_CSV_URL`）と掲載用タブ（`EVENTS_FORM_CSV_URL`）の両方。
   - (b)(c) の場合は、取得失敗と同じく前回分を使う（`parse_sheet_csv` が None を返す）。
     (c) を足した理由：フォームの質問タイトルや「承認」の見出しが変わると、掲載用タブの数式が `#N/A` を返す。
     これを通常の行として読むと「読めない行が1つあるだけ」になり、フォーム分が黙って全部消えるため（2026-09-28、手順書の数式を書いたときに判明）。
   - 1つでもあれば、環境変数 `GITHUB_OUTPUT` があるときに `sheet_error=true` と `sheet_error_detail=<シート名と理由>` を書き出す。
     終了コードは0のまま（自動抽出分や前回分でイベント一覧の更新は続ける）。
   - 行単位の読み取りエラー（`warnings`）では通知しない（前回どおり `_events_*.json` に記録するだけ）。

## 設計判断の理由（なぜこの設計にしたか）

- **Googleフォーム＋スプレッドシート**：既存のスプレッドシート連携と `parse_sheet_csv` をそのまま使え、サーバー・有料サービス・ログインの仕組みがいらない。
  フォームの「日付」形式で日付の書き間違いが起きない。静的サイトのまま実現できる。
- **承認は「承認」列に書くだけ**：既存の「非表示」列と同じ「何か書いてあれば」という決まりにそろえた。チェックボックスにしないのは、フォームの回答で行が増えたときに入力規則が付かない場合があるため。
- **連絡先を掲載用タブに出さない**：回答タブをそのまま公開すると連絡先が誰でも見られるうえ、`_events_*.json` 経由でリポジトリとPagesにも残ってしまう。
  公開するのは、数式で必要な列だけを抜き出した掲載用タブに限る。
- **列を見出しの文字で探す**：フォームに質問を足すと回答タブの列の並びが変わる。列の位置で指定すると、場所の欄にイベント名が入るようなずれが気づかれないまま起きるため。
- **優先順位を「自動 < フォーム < シート1」にする**：主催者の情報は自動読み取りより正確なことが多い。一方で、吉野さんがシート1で直接書いたものは最終判断として常に勝つようにし、どの経路のイベントも同じ非表示行で消せるようにした。
- **変更・中止はスクリプトで自動処理しない**：どの掲載を変えるのかを申し込みから機械的に特定するのは難しく、なりすましで他人のイベントを消される危険もある。吉野さんが確認して承認を付け替える運用にした。
- **失敗は通知するがワークフローは止めない**：シートの問題でサイト全体のデプロイが止まるのは影響が大きすぎる。前回分で表示を続けつつ、Issueで気づけるようにした。
  既存の「イベント側の失敗でIssueを起票しない」（イベントタブ設計書）は、シートの読み込み失敗に限ってこの設計で変更する。

### 既知の制限（v1では対応しない）

- チラシ画像は載せられない。
- 「中止」をサイト上に表示できない（一覧から消えるだけ）。
- 反映は最大で翌朝まで遅れる（急ぐときは手動実行）。

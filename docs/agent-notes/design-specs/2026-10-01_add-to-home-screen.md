## 概要

サイトをスマホのホーム画面に置けるようにし、そのためのボタンと手順の案内を付ける。
毎朝更新される「最新のお知らせ」を見に来てもらうには、検索やLINEの履歴からたどるより、
ホーム画面から1回で開けるほうがよい。

先に、ブラウザの仕組み上できること・できないことを整理しておく（設計全体の前提）。

| やりたいこと | できるか | 補足 |
|---|---|---|
| Android（Chrome等）で、ボタンを押すと追加の確認が出る | できる | サイト側に「マニフェスト」とアイコンを置くと、ブラウザが追加用の合図（`beforeinstallprompt`）を出す。ただし**訪問してすぐには出ない**（1回タップし、合計30秒ほど見たあとに出る） |
| iPhone / iPad で、ボタンを押すと追加される | **できない** | Appleが仕組みを用意していない。利用者自身が共有メニューから「ホーム画面に追加」を選ぶ必要がある。サイト側は手順を見せることしかできない |
| LINEなどのアプリ内で開いた画面から追加する | **できない** | SafariやChromeで開き直してもらう必要がある。共有リンクはLINEで届くことが多いので、この案内は必須 |
| ボタンを押すとブックマークに入る | **できない** | どのブラウザも、サイト側からブックマークを追加する操作を許可していない。手順（PCなら Ctrl + D）を見せることしかできない |

したがって作るものは、**「押せば追加できる環境では追加の確認を出し、
それ以外では、その端末に合った手順を見せるボタン」**になる。

現在のサイトにはアイコンが1枚も無い（ブラウザのタブに出る小さなアイコンも無い）。
このままホーム画面に追加すると、iPhoneでは画面の縮小画像、Androidでは頭文字だけの
アイコンになるため、アイコンの作成も今回の範囲に含める。

- 地色 `#1B4B5A`（`bay`）の正方形に、`#F2F1EC`（`paper`）で「み」1文字。

### 4. ボタンを押したときの動作

```
[ホーム画面に追加] / ［追加方法］ を押す
  ├ ブラウザから追加用の合図（beforeinstallprompt）を受け取っている
  │   → ブラウザの追加確認を出す（deferredPrompt.prompt()）
  │       ├ 追加された  → 仕様2のセクションと仕様3のお知らせを隠す
  │       └ やめた      → 何もしない（エラー表示もしない）
  │     ※ 合図は1回しか使えない。使ったら変数を空にし、次に押されたら下の手順表示へ
  └ 受け取っていない（iPhone・LINE内・訪問直後のAndroid・PCのFirefox等）
      → 手順の画面を開く（下記）
```

合図の受け取り方：

```js
let deferredPrompt = null;
window.addEventListener('beforeinstallprompt', (e) => {
  e.preventDefault();          // ブラウザ独自の帯が二重に出ないようにする
  deferredPrompt = e;
});
window.addEventListener('appinstalled', () => { /* セクションとお知らせを隠し、dismissed を保存 */ });
```

- このリスナーは**スクリプトの先頭付近で、データ読み込み（`init()`）を待たずに登録する**。
  合図はいつ届くか分からないため。
- **合図が届いていないことを理由にボタンを隠したり無効にしたりしない。**
  合図は訪問してしばらく経たないと届かず、iPhoneには永久に届かない。
  ボタンは常に押せて、届いていなければ手順を見せる。

端末の判定（**手順の並べ方を変えるためだけに使う**。判定が外れても全手順が読める）：

```js
function detectPlatform() {
  const ua = navigator.userAgent || '';
  const isIOS = /iPhone|iPad|iPod/.test(ua)
    || (navigator.platform === 'MacIntel' && navigator.maxTouchPoints > 1); // iPadはMacと名乗る
  const isAndroid = /Android/.test(ua);
  const inApp = /\bLine\/|FBAN|FBAV|Instagram/i.test(ua);  // LINE・Facebook・Instagramのアプリ内
  return { os: isIOS ? 'ios' : (isAndroid ? 'android' : 'desktop'), inApp };
}
function isStandalone() {
  return (window.matchMedia && window.matchMedia('(display-mode: standalone)').matches)
    || navigator.standalone === true;   // 後者はiPhone用
}
```

**手順の画面**は、既存の詳細モーダル（`#modal` / `#modal-content`）を使う。

- `openModal(item)`（[index.html:551-583](../../../src/index.html#L551-L583)）のうち、

### 5. ホーム画面から開いたときに古い情報が残らないようにする

`display: standalone` で開いた画面には、再読み込みのボタンが無い
（iPhoneでは引っぱって更新もできない）。アプリを閉じずに翌日また開くと、
**前日に読み込んだ内容のまま**表示される。毎朝更新されるサイトなので、次の処理を入れる。

```
画面が再び表示された（visibilitychange で visible になった）とき
  └ 前回の確認から30分以上たっていれば
      → ./data/life_info.json を取得（cache: 'no-store'）
          ├ last_updated が、表示中のものと違う → location.reload()
          ├ 同じ                                 → 何もしない
          └ 取得に失敗（圏外など）               → 何もしない（エラー表示もしない）
```

- 表示中の `last_updated` は、`init()` で読んだ値
  （[index.html:1174](../../../src/index.html#L1174)）を `state.lastUpdated` に保存しておく。
- **単純に「時間がたったら再読み込み」にはしない。** 圏外で再読み込みすると、
  ブラウザのエラー画面になり、そこから戻る手段が無くなる。
  先にデータを取得できたときだけ再読み込みする。
- 詳細モーダルを開いている最中（`#modal` が表示中）は再読み込みしない。次の機会に回す。
- `init()` でデータ読み込みに失敗している場合（`state.mainDataLoaded` が false）は、
  30分の間隔を待たずに確認する（電波が戻ったら自動で復帰できる）。
- 通常のブラウザで開いている場合にも同じ処理が動くが、害は無い
  （タブを開きっぱなしの人にも新しい情報が出る）。
- 再読み込みするとハッシュ（`#base-...`）は保たれるので、共有リンクの動作は変わらない。

## 検証の方法

**1. ローカルで実際に開く**（本番と同じ構成を組み立てる。コピーするものが増えた点に注意）

```bash
mkdir -p /tmp/dist && cp src/index.html /tmp/dist/index.html \
  && cp -r public/. /tmp/dist/ && (cd /tmp/dist && python -m http.server 8765)
```

`http://localhost:8765/` で開く（`file://` ではマニフェストが読まれない）。

## 設計判断の理由（なぜこの設計にしたか）

### なぜ「ブックマークに追加」をボタンにしないか

サイト側からブックマークを追加する方法は、現在のどのブラウザにも無い
（昔のInternet Explorerにはあったが廃止された）。押しても何も起きないボタンを置くより、
キー操作（Ctrl + D）とメニューの場所を一文で示すほうが正直で、確実に伝わる。

### なぜボタンを常に押せるようにするか（合図を待って出す方式にしないか）

よくある実装は「`beforeinstallprompt` が届いたらボタンを出す」だが、この合図は
iPhoneには届かず、Androidでも訪問直後には届かない。この方式だと、
水俣市の利用者の多くを占めると思われるiPhoneでは**ボタンが一度も出ない**。
合図があれば使い、無ければ手順を見せる形にすれば、どの端末でも同じ場所に同じボタンがある。

### なぜ端末の判定を「並べ替え」にだけ使うか

端末の判定（ユーザーエージェント）は外れることがある（iPadはMacと名乗る、
アプリ内ブラウザは種類が多い等）。判定結果で手順を出し分けて他を隠すと、
外れたときに正しい手順が読めなくなる。先頭に出すものを変えるだけなら、
外れても「ほかの端末の場合」を開けば読める。

### なぜ Service Worker を入れないか

以前はAndroidで追加の確認を出すために必須だったが、現在は不要
（必要なのはマニフェスト・192pxと512pxのアイコン・https）。
Service Worker の主な役割はオフライン表示のためのキャッシュだが、
このサイトは毎朝データが変わるため、キャッシュの扱いを誤ると
**古い情報を出し続ける**。直すには利用者側でキャッシュを消してもらう必要があり、
原因の切り分けも難しい。オフラインで読む必要性も低いので、入れない。

### なぜ `display: standalone` か

`browser`（通常のブラウザで開く）にすると、Androidで追加の合図が出なくなり、
「ボタンを押すと追加できる」が実現できない。`minimal-ui` はiPhoneが対応していない。
`standalone` の欠点（再読み込みの手段が無い）は仕様5で補う。

なお、iPhoneではホーム画面から開いた画面とSafariとで**保存領域が別**になる。
Safariで設定した子育てタブの絞り込みは、ホーム画面から開いた側には引き継がれない
（もう一度選べば、以後はそちらに保存される）。回避する方法は無いので、そのままとする。

### なぜフィードタブに一行のお知らせを出すか（ページ下部だけにしないか）

ページ下部は約190件の一覧の下にあり、ほとんどの人が到達しない。
一方で、全画面を覆う案内や、何度も出る帯は、2026-08-26に決めた
「誘導的な言い回しを避ける」方針に合わない。そのため
「事実を一行、スマホのみ、一度消したら二度と出ない」に留めた。

### 今回やらないこと

- **プッシュ通知**：2026-09-18に見送りを決定済み。今回ホーム画面に追加できるようになっても
  サーバーが必要な点は変わらない。
- **OGP画像（`og:image`）**：今回アイコンができるので設定は可能になるが、
  LINEでの見え方が変わるため、別途相談のうえで行う。
- **LINEから直接ブラウザで開かせる仕組み**（URLに `openExternalBrowser=1` を付ける方法）：
  共有リンクの形式を変えることになるため入れない。

## 概要

イベントタブで、**申し込みが必要なイベントについて「申し込みが必要か」「いつまでか」「どう申し込むか」が分かる**ようにする。
吉野さんとの相談（2026-10-06〜07）で、次の3つ（相談時の案A・B・C）を入れることにした。

- **A. カードに申し込み情報を出す**：「要申込」「一部要申込」「申込不要」の印、締切日、申込方法。
- **B. 締切を過ぎたら「受付終了」と出す**：締切日と今日の日付から、画面側で判定する。
- **C. タブ上部に「申し込みの締切が近いイベント」をまとめる**：締切日の順に並べる。

背景：2026-10-06時点で掲載中の15件の元ページを確認したところ、申し込みかチケットが必要なものが5件、
一部だけ申し込み制のものが1件あった。しかし今のカードには申し込みの情報が出ていない
（AIの要約にたまたま「事前申し込みが必要」と入った2件だけ）。
一覧は開催日の順に並ぶため、**開催日より前にある締切が目に入らず、気づいたときには締切を過ぎている**ことが起きる
（例：sunset YOGA は開催10/10・締切10/8）。

## データ構造

### `events.json` の各イベントに3項目を追加

```
{
  …既存の項目（id, title, start_date, end_date, time_text, venue, summary, organizer, source_url, source_label, origin）,
  "registration": "required" | "partial" | "not_required" | null,
  "registration_deadline": "YYYY-MM-DD" | null,
  "registration_note": "string（50字以内）" | null
}
```

| 項目 | 意味 |
|---|---|
| `registration` | `required`：参加・入場に事前の申し込み・予約・チケット購入が必要。<br>`partial`：一部の企画だけ事前申し込みが必要（例：スポーツフェスタの中のバスケットボール教室）。<br>`not_required`：**記事に**「申込不要」「自由参加」「当日受付」などと**書いてある**。<br>`null`：書いていない・読み取れない。**推測で `not_required` にしない。** |
| `registration_deadline` | 申し込みの締切日（その日まで受け付ける）。記事に日付が書いてあるときだけ。「定員になり次第締切」だけのときは `null` |
| `registration_note` | 申込方法と条件を短く。例：「チラシのQRコードから。定員20名」「電話・FAX・メールで（84-9996）」「各参加店舗へ電話で」 |

- 3項目は**常に出力する**（値が無ければ `null`）。画面側は項目が無い古いデータでも動くようにする。
- 次の場合は `registration_deadline` を `null` にする（読み違いの可能性が高いため）：
  日付として読めない／`end_date` より後。
- 締切は `registration` が `required` か `partial` のときだけ持つ（締切だけが表示される不自然な状態を作らない）。
- 申込方法は `registration` が `null` のときは持たない。`not_required` のときは、当日の受付方法などの補足として持ってよい
  （画面仕様1の「申込不要」の行で表示する）。
  ※ 2026-10-07 実装時に修正：当初は `not_required` でも申込方法を `null` にすると書いていたが、画面仕様1と矛盾していたため画面仕様に合わせた。
- 申込方法は60字を超えたら切り詰め、URLは取り除く（自動抽出分のみ。手で書いたシートの値は切らない）。
- **本文による裏づけ**（2026-10-07 実装時に追加）：自動抽出では、AIの判定を記事本文の言葉で確かめる。
  - `not_required` は、本文に「申込不要」「予約不要」「自由参加」「直接会場へ」「当日受付」「会場・テント等で受付」などの言葉が無ければ `null` にする。
  - `required` / `partial` は、本文に「申込」「予約」「チケット」「前売」「整理券」「応募」「エントリー」「受付終了」のどれも無ければ `null` にする。
  - 理由は「タスク1の結果」参照（AIが本文に無い文を作って「申込不要」にした例があった）。

### `_events_auto.json`（自動抽出のキャッシュ）

- 各エントリに `"schema": 2` を付ける。
- **`schema` が無い（2未満の）エントリで、`event` があり、まだ終わっていない（`end_date` が今日以降）もの**は、
  1回だけ判定し直して申し込み情報を取り出す。終わったイベントと、イベントではないと判定済みの記事は判定し直さない。
  2026-10-07時点では対象は15件前後で、1日の上限（`EVENTS_MAX_GEMINI_CALLS`、40件）に収まる。
- 判定し直しで Gemini の呼び出しに失敗したエントリは、古いエントリをそのまま使う（イベントが一覧から消えないように）。翌日また試す。
- 判定し直しでは**申し込み情報だけ**を足し、開催日・会場などは掲載済みの内容を変えない。
  判定し直しの結果が「イベントではない」「開催日が分からない」に揺れても、申し込み情報は使い、掲載は続ける
  （2026-10-07 実装時に明記。試し実行でまちゼミの判定が揺れたため）。

### 手動登録用シート（シート1）と投稿フォームに3列を追加

| 見出し（文字どおり） | 入れる値 | `events.json` での値 |
|---|---|---|
| `申込` | `必要` / `一部必要` / `不要` / 空欄 | `required` / `partial` / `not_required` / `null` |
| `申込締切` | 日付（既存の開始日と同じ形式） | `registration_deadline` |
| `申込方法` | 50字以内 | `registration_note` |

- **3列とも任意**（必須列は「イベント名」「開始日」のまま）。列が無いシートも、これまでどおり読める。
  そのため、スクリプトの変更を先に入れ、シートの列は後から足せる。
- `申込` に上の4つ以外が書いてあるとき、`申込締切` を日付として読めないときは、その項目を空欄として扱い、
  既存と同じく行の警告（`warnings`）に記録する（Issueにはしない）。
- **上書き行で申込の列が空欄のとき**は、置き換え先の自動抽出分の値を引き継ぐ
  （今ある上書き行は申込の列ができる前に作られたため。既存の「情報元」の引き継ぎ `_fill_source_label` と同じ考え方）。
  上書き行で「申込不要」などと書いてあれば、そちらを優先する。

## 処理仕様（`scripts/update_events.py`）

1. **抽出プロンプト**（`EVENT_EXTRACTION_SYSTEM_PROMPT`）の出力に3項目を足し、次のルールを書く。
   - 対象は「タイトルが示す催し」（既存のルールと同じ）。
   - `required`：参加・入場・観覧のために事前の申し込み・予約・チケット購入・整理券の事前入手が必要。
   - `partial`：催しの中の一部の企画だけが事前申し込み制で、ほかは自由に参加・来場できる。
   - `not_required`：「申込不要」「自由参加」「どなたでも」「当日会場で受付」など、事前の申し込みが要らないことが本文に書いてある。
   - 書いていなければ `null`。**祭りやマルシェだからといって `not_required` と推測しない。**
   - 締切は「申込締切」「〆切」「〜日まで」など、申し込みの期限として書かれた日付だけ。受付開始日・開催日・チラシの掲載日を入れない。
   - `registration_note` は50字以内。申込方法（QRコード・電話・メール・窓口・各店舗など）と、定員・先着・抽選の別。
     電話番号は記事に書かれているものだけ。URLは入れない（カードの「詳細を見る」から元のページに行けるため）。
2. **キャッシュの判定し直し**（`update_auto_cache`）：上記 `schema` のとおり。判定し直しの対象は、未判定の記事より**後**に回す
   （新しい記事の掲載が遅れないように）。上限 `MAX_GEMINI_CALLS` は合計で数える。
3. **シートの読み込み**（`parse_sheet_csv`）：3列を読む。
4. **統合**：上書き行の空欄の引き継ぎ（上記）。
5. 並び順・終了済みの除外など、既存の処理は変えない。**「受付終了」の判定はスクリプトでは行わない**（画面側で行う。理由は後述）。

トーン（`paper`/`ink`/`bay`、明朝見出し）は変えない。文言は**事実だけを書き、急かす言い回しを使わない**
（2026-08-26の方針。「お早めに」「残りわずか」「あと2日」は使わない）。

### 1. カードの申し込み情報（案A・B）

時間・場所の行（[index.html:1315-1319](../../../src/index.html#L1315-L1319)）の**直後**に1行足す。

```
10/10(土)
『sunset YOGA』～海×夕日×ヨガ～
🕒 17:00〜18:00   📍 エコパーク水俣 親水護岸
［要申込］ 10/8(木)締切 ・ チラシのQRコードから。定員30名程度
どんな催しか…（要約）
```

| 状態 | 印 | 印の色 | 印のあとに続ける文字 |
|---|---|---|---|
| `required` で締切前（または締切不明） | 要申込 | `bg-warnAccentSoft text-warnAccent` | 締切があれば「M/D(曜)締切」、続けて `registration_note` |
| `partial` で締切前（または締切不明） | 一部要申込 | 同上 | 同上 |
| `required`／`partial` で**締切日 < 今日** | 受付終了 | `bg-line text-inkSoft` | 「M/D(曜)締切」 |
| `not_required` | 申込不要 | `bg-baySoft text-bay` | `registration_note` があれば続ける |
| `null` | （行ごと出さない） | | |

- 印は `text-[11px] font-bold px-1.5 py-0.5 rounded`。行全体は `text-xs text-inkSoft`、2行を超える分は省略（`line-clamp-2`）。
- 締切日の表示は既存の `formatEventDateRange(deadline, deadline)` と同じ形式（年が違えば年を付ける）。
- **締切日が今日のとき**は「今日締切」と書く（印は「要申込」のまま）。
- **受付終了でもカードは一覧から消さない。** 一部の企画だけの受付終了（例：バスケットボール教室）や、
  当日枠・観覧のみ可能な催しがあるため。開催日を過ぎたら、これまでどおり一覧から消える。
- 「受付終了」の判定は、締切日と**画面を開いた端末の今日の日付**で行う（毎朝のデータ更新を待たずに切り替わる）。
  今日の日付は既存の `getLocalDateString()` を使う。

### 2. 「申し込みの締切が近いイベント」（案C）

`#events-content` の先頭、「今日・開催中」グループの**前**に置く。

```
申し込みの締切が近いイベント
┌──────────────────────────────────┐
│ 10/8(木)締切   sunset YOGA ～海×夕日×ヨガ～        │
│                開催 10/10(土)                   ›  │
│ 10/11(日)締切  水俣環境アカデミア プログラミング…  │
│                開催 10/17(土)                   ›  │
└──────────────────────────────────┘
※ 締切は元のページから読み取ったものです。申し込む前に元のページでご確認ください。

今日・開催中
…（既存の一覧。これまでどおり開催日順）
```

- 対象：`registration` が `required` か `partial`、`registration_deadline` が**今日から14日後まで**（今日を含む）。
  締切日の早い順、同じ日なら開催日の早い順。**件数の上限は設けない**（14日の範囲で自然に絞られる）。
- 対象が0件ならセクションごと出さない。
- 締切が書いていない「要申込」のイベントは、締切順に並べられないので**ここには出さない**（カードの印だけ）。
- 見出しは既存のグループ見出しと同じ様式（`font-serif font-medium text-[15px] border-l-2 border-bay/40 pl-3`）。
- 各行は**カードの複製ではなく、1件1行（2段）の短い要約**にする。カード本体は下の一覧に1回だけ出る。
  - 1段目：「M/D(曜)締切」（今日なら「今日締切」）を `text-xs font-bold text-warnAccent`、続けてイベント名（1行で省略）。
  - 2段目：「開催 M/D(曜)」（期間なら既存の期間表示）を `text-[11px] text-inkSoft`。
  - 枠は既存カードと同じ `bg-white rounded-xl border border-line`、行の区切りは `divide-y divide-line`。
- 行を押すと、**下の一覧の該当カードまでスクロールする**。
  - カードに `id="event-{id}"` を付ける。行は `<button type="button">` にし、JSで `scrollIntoView` する。
    **`<a href="#event-…">` にしない**（URLのハッシュが変わり、制度カードの共有リンクの処理 `handleHashRoute` が動いてしまうため）。
  - イベントタブのヘッダーも上部に固定されているので、スクロール先がヘッダーに隠れないようにする。
    既存の `updateHeaderOffsets()`（[index.html:1176](../../../src/index.html#L1176)）に `#view-events header` 用の
    `--events-header-h` を足し、カードに `scroll-margin-top` を当てる（子育てタブの `.scroll-mt-header` と同じ方式）。
  - 移動先のカードを1.5秒ほど枠の色（`ring-2 ring-bay/40`）で示し、どれに移動したか分かるようにする。
    `prefers-reduced-motion` のときもこの表示は残してよい（動きではないため）。
- 下の注意書き（※）は `text-[11px] text-inkSoft`。

## 設計判断の理由（なぜこの設計にしたか）

### なぜ締切が近いものを別の欄にまとめるか（一覧の並び順自体は変えないか）

申し込みが必要なイベントにとって、行動の期限は開催日ではなく締切日である。
一方、一覧の大半（当日ふらっと行ける祭り・マルシェなど）にとっては開催日の順が自然で、
一覧全体を締切順に並べ替えると、締切の無いイベントの置き場所が無くなる。
そのため、一覧は開催日順のまま、締切が迫っているものだけを上に短くまとめる形にした。
カードを複製せず1行の要約にしたのは、同じカードが2回出て一覧が長くなるのを避けるため。

### なぜ「14日以内」か

2026-10-06時点で締切日が書かれていた2件は、開催の2日前（sunset YOGA）と6日前（プログラミングセミナー）だった。
件数が少ないので傾向とまでは言えないが、締切は開催の1〜2週間前までに来ることが多いと見込んでいる。
14日あれば、週末に一度サイトを見る人でも次の締切に2回は気づける。
これより長くすると、欄が長くなり下の一覧が埋もれる。

### なぜ「申込不要」は書いてあるときだけにするか

「申込不要」と表示して実際は要予約だった場合、利用者は当日行って入れない。
「要申込」の見落とし（印が出ないだけ）より実害が大きい。
祭りの多くは申し込みについて何も書いていないため、印が出ない（`null`）イベントが多くなるが、それでよい。

### なぜ「受付終了」は画面側で判定するか

データは1日1回しか更新されないため、スクリプトで判定すると、締切日の翌朝7時まで「要申込」のまま残る。
画面を開いた時点の日付で判定すれば、その日のうちに正しく切り替わる。

### なぜ定員到達による受付終了は扱わないか

「定員に達したため受付を終了しました」は、記事の掲載後に同じURLのまま書き足される。
今の収集の仕組みは、一度判定した記事を読み直さない（2026-08に「最新のお知らせ」で判明した構造的な取りこぼしと同じ）。
これを拾うには、開催前のイベントの元ページを毎日読み直す仕組みが必要で、
市のサイトへのアクセスとGeminiの呼び出しが毎日増える。今回は締切日による判定だけにし、
カードと欄の注意書きで「元のページで確認」を促す。必要になったら別途設計する。

### なぜ申込方法のURLを載せないか

元ページへのリンク（「詳細を見る」）が既にあり、申込フォームのURLを別に載せると、
AIが読み違えたURLや期限切れのフォームに直接誘導する危険がある。申し込みは元ページから行ってもらう。

## 吉野さんに確認した点（2026-10-07、3点とも提案どおりで了承）

1. **「締切が近い」の範囲**：14日。
2. **フォームの「申込」**：必須にする。
3. **印の文言**：「要申込」「一部要申込」「申込不要」「受付終了」。
